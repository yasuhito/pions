これは一次資料を用いた静的調査である。パッケージのマニフェストと TypeScript/JavaScript、Markdown、設定ファイルを調査した。いかなるパッケージもインストールまたは実行して**いない**。以下の「ソース上の事実」は、引用した実装について述べる。「推奨事項」は最終セクションに限定する。

## 要求された観点別のソース事実の統合

### パッケージ形態とエントリーポイント

実装は、実質的に異なる4つの形態に分かれる。

1. **真の Pi 子ランタイム：** `pi-herdr-agents`、両方の `pi-herdr-subagents` バリアント、`@minhduydev/pi-subagents`、`@yofriadi/pi-subagent-herdr`、`pi-pier`、Shepherd/Shepherdr、`@tian.zuo/pi-subagents`、`pi-herdr-live-agents`、および planning bundle。これらは親側ツールと、通常は制限された子側の completion/reporter ツールを登録する。
2. **Herdr 制御基盤：** `@ogulcancelik/pi-herdr`、`@sfroment/pi-herdr`、`@andrewjacop/pi-herdr`、`@henryqw/pi-herdr`、および `pi-terminal-mux`。これらは surface/process を管理するが、それ自体で永続的な親子セマンティクスを確立するわけではない。
3. **Workflow/crew レイヤー：** `ry-skill`、`@itc-steve/pi-herdr`、`mu`、`pi-herdr-squad`、`@ret2hell/pi-herdr-orchestrator`、Apnea、Agent Fleet、および planning bundle。これらは stage、DAG、role、review、または setup policy を追加する。
4. **周辺ユーティリティ：** title/status/fork/worktree/todo/terminal/peer/notification パッケージ。これらは有用なコンポーネントまたは UX の先行例だが、subagent harness ではない。

### ライフサイクルと Herdr 統合

ソースには3種類の完了判定主体が見られる。

- **明示的な子アーティファクト/ツール：** qcts、live-agents、Shepherd、squad、Tian、および Pier。これにより型付けされた終端結果が得られ、ネストに最も安全である。
- **Pi セッション/イベント境界：** qcts は `agent_settled` を待つ。subagent ファミリーは Pi イベントからアクティビティを記録する。Pier はセッションの custom entry をリプレイする。これにより、中間的な `agent_end` を最終結果として扱うことを避けられる。
- **Herdr 状態/ターミナル観察：** 汎用 Herdr ツールと旧来の orchestrator は、native agent state、terminal stability、output marker、または ledger text を待つ。これは liveness には有用だが、唯一の意味的完了シグナルとしては弱い。

本格的な統合はすべて、focus に依存する keystroke ではなく Herdr ID を使用する。より安全なものは、自身が作成した surface と呼び出し元所有の surface を区別し、終了を証明できない場合には証拠を保持する。

### モデルと思考設定

繰り返し見られる優先順位は、**明示的な呼び出し → role/profile → package/global config → 親ランタイム**である。`pi-herdr-agents`、legacy `pi-herdr-subagents`、qcts、squad、および live-agents は、正確な Pi model ID とサポートされる thinking level を検証する。一方、`@itc-steve/pi-herdr` はデフォルトの local model と、順位付けされた「think」model を振り分ける。Shepherd では role が最優先であり、Tian では profile が最優先である。`mu` は意図的に model/thinking を選択せず、起動コマンドを環境設定に委ねる。

暗黙の fallback は一般に危険である。より優れたパッケージは、利用できない固定 model を拒否するか、どの fallback が選択されたかを報告する。qcts 実装は、観測されたランタイム詳細も完了証拠に記録する。

### ネスト

レビューした設計のうち、任意のネストに対して実質的に肯定的な材料を提供するのは3つだけである。

- **qcts：** 明示的な親/子孫の所有関係、continuation batching、子孫が settle するまで遅延される完了、子孫の drain 後のキャンセル確認、および同一 self-type の直接再帰の拒否。
- **MinhDuy：** 再帰的な handle/scope API、および境界付き settlement reporting を伴う子孫優先の stop。
- **pi-herdr-agents / legacy pi-herdr-subagents：** 子ツールを有効なままにでき、role 単位の `spawning: false`/deny 制御を備える。柔軟だが、構造的な厳密さは低い。

複数のパッケージはネストを意図的に禁止しており（`@yofriadi/pi-subagent-herdr`、live-agents、Pier のデフォルト worker、squad）、ほかのものはインストール済み extension が子で読み込まれるため偶発的な再帰が可能なだけである（`@andrewjacop/pi-herdr`）。偶発的に利用可能であることは、ネストプロトコルではない。

### 永続化と履歴

- **強力で永続的な制御状態：** MinhDuy の run/task store と `mu` の SQLite/WAL DAG。
- **セッションイベントソーシング：** Pier と todo-herdr は Pi session entry を使用し、自然に session branch/reload のセマンティクスに従う。
- **永続的な append log：** ry-skill pipeline、ITC journal、workflow journal、および peer mailbox。
- **一時的な操作アーティファクト：** qcts は意図的に子の Pi session persistence を無効化し、新しい親プロセスでは古い結果を復旧しない。
- **人間が読める子の履歴：** pi-herdr-agents と live-agents は実際の Pi session/pane history を保持する。live-agents は pane を保持することを明示している。

### 障害、キャンセル、およびセキュリティ

最も堅牢な障害対応パターンは次のとおりである。新しく作成した surface のみをロールバックする。呼び出し元所有または証拠を含む surface を保持する。turn interrupt と process cancellation を区別する。プロセスの終了を証明できない場合は「unknown」と報告する。終端結果を single-writer/at-most-once にする。親のキャンセルを確認する前に子孫をキャンセルする。

一般的なセキュリティ上の制約も、一次ソースで明示されている。

- Herdr pane、Git worktree、VM、または Worker thread は、OS のセキュリティサンドボックスでは**ない**。
- 任意の Bash が利用可能なままなら、読み取り専用という role の主張は強制できない。
- 汎用 Herdr wrapper は破壊的な process/session 操作を公開する。
- argv 内の task text はプロセス一覧で見える可能性がある。prompt file/mailbox はその露出を減らす。
- peer と子の出力は信頼できない model input であり、サイズ制限と delimiter/framing による防御が必要である。
- remote SSH helper、custom CLI template、`--yolo`、`--dangerously-skip-permissions`、および `sudo sh -c` は、実装上の便宜ではなく、意図的に高い信頼を要求する境界である。

## Python harness への推奨事項（ソース事実ではない）

1. **小規模な双方向プロトコルを使用する。** 親で Python supervisor を実行し、spawn したすべての pane で最小限の child reporter plugin/helper を実行する。各操作にランダムな ID と capability token を与える。reporter は型付けされた `started`、`activity`、`blocked`、`completed`、`failed`、および `cancelled` レコードを出力する。terminal output は可観測性のためだけに用いる。
2. **系譜を第一級の概念にする。** `operation_id`、`parent_operation_id`、`root_operation_id`、depth、child IDs、Herdr workspace/tab/pane IDs、Pi session reference、model/thinking、cwd/worktree、state sequence、および cancellation epoch を永続化する。最大 depth、fan-out、live descendant 総数、および budget を強制する。明示的に許可されていない限り、同一 profile の直接再帰を拒否する。
3. **qcts 方式の settlement を採用する。** ノード自身は settle 済みでも、子孫がまだ実行中であり得る。直接の子孫と保留中の result handoff が drain した後にのみ、親の完了を公開する。キャンセル時には、新しい子の作成をアトミックに凍結し、子孫優先で伝播し、期限まで待機し、failure/unknown を記録してから上流へ確認応答する。
4. **qcts より強力なクラッシュ復旧を追加する。** mode-`0700` の harness directory 内で、SQLite の WAL mode（または厳密にロックされた append-only JSONL）を使用し、アーティファクトには mode-`0600` を設定する。起動時に、記録を Herdr の native agent identity と照合する。「latest session を採用」してはならない。正確な operation、pane、および child-session identity を必須とする。
5. **shell ではなく、必ず `asyncio.create_subprocess_exec` を使用する。** Herdr を argv 配列として渡し、ID/enum を検証し、stdout/stderr/timeout に上限を設ける。task prompt はコマンドライン引数ではなく、非公開ファイルまたはローカルの認証済み socket に置く。汎用的な「任意の Herdr subcommand」model tool を提供しない。
6. **liveness と意味的完了を分離する。** Herdr event を subscribe するか native `agent get` を poll して process/liveness を確認する。意味的結果は、認証済みの子 channel を通じてのみ受け入れる。`agent_end` は中間状態として扱い、`agent_settled` と子孫の drain を合わせて終端とする。
7. **spawn 時にランタイムポリシーを snapshot する。** 正確な provider/model ID と thinking level を一度だけ解決して検証し、operation とともに記録して明示的に渡す。resume/recovery 時に model を暗黙に変更したり、tools を拡張したりしない。
8. **pane を可視かつ所有権上安全に保つ。** focus を奪わない background tab/pane をデフォルトとし、failed/blocked pane は調査用に保持し、supervisor 所有として記録された surface のみを閉じる。`interrupt turn`、`cancel subtree`、`close surface`、および `forget history` の操作を分けて提供する。
9. **worktree を sandbox ではなく整合性確保のツールとして扱う。** 排他的な writable scope または書き込みを行う subtree ごとに1つの worktree を使用する。ただし、敵対的コードを対象とする場合は child tool allowlist と OS レベルの制御を組み合わせる。Bash が読み取り専用だと主張してはならない。
10. **model 間のすべてのデータに上限を設ける。** task/result/history のサイズを制限し、信頼できない child/peer text を frame 化・escape し、永続化前に secret を redact し、大きすぎる結果には hash と pointer を保存する。各 terminal result は最大1回だけ配信する一方、リプレイ可能な監査用永続記録を保持する。

実用的な実装順序は、**(1)** live-agents 方式の可視 pane + capability mailbox、**(2)** qcts 方式の lineage/descendant settlement/cancellation、**(3)** Pier 方式の event-sourced recovery、続いて **(4)** オプションの MinhDuy/mu 方式の durable scheduling、claim、review、および worktree である。これにより、ワークフロープラットフォーム全体を再現するのではなく、初期の Python module を奥深くテスト可能なものに保てる。
