# 実PiとHerdrによるE2E検証

Issue #114のリリースゲートとして`scripts/e2e-real-pi-herdr.mjs`は、公開相当の`@yasuhito/pions@0.1.0` tarballを一時的な新規npm利用先へ導入し、そのインストール済み拡張を本物のPiとHerdrで自動検証する。状態、npmキャッシュ、利用先、ワーカーの共有作業ディレクトリは一時ディレクトリへ隔離し、既存のHerdrセッション、利用者ワークスペース、Pionsのリポジトリ外保存状態は変更しない。Herdrライフサイクルを管理する監督側から起動済みの非defaultセッションと呼び出しラッパーを渡すこともできる。

## 実行方法

```bash
npm run test:e2e
```

`npm run test:e2e`は、パッケージ内容検査、tarball作成、新規利用先へのnpm導入、隔離環境の準備、検証、後始末までを行う。`npm run release-gate`は通常の全品質検査とこの実環境検証をひと続きで実行する。CI(`npm run check`)には含めない。実際のモデル呼び出しを伴うため、実行のたびに料金と数十秒から数分程度の時間がかかる。

## 必要条件

- Node.js 26以上(CIと同じ)
- `herdr`がPATH上にあること(検証時点の動作確認は0.9.0)
- `pi`がPATH上にあること
- `~/.pi/agent/auth.json`にPiのLLM認証情報があること
- `.pions.json`の`model`が指すプロバイダー・モデルが認証済みであること(`pi auth check --provider <provider> --model <id>`で確認できる)

いずれかが満たされない場合、スクリプトは検証を始める前に理由を示して失敗する。

## 何を検証するか

1. **tarball利用先とツール面**: `npm pack`で作成したtarballを新しい一時利用先のnpm依存としてインストールし、そのインストール済み拡張をPiへ読み込む。実際の親Piが登録するPionsツールは`pions_delegate`、`pions_result`、`pions_operation`の3つだけであることを検証する。
2. **既知のUTF-8最終回答**: 親のPiセッションに`pions_delegate`を1回だけ使うタスクを渡す。タスクは絵文字と日本語を含むランダムな既知文字列を`bash`の`printf`で出力させ、同じ文字列を`write`で作業ディレクトリ直下の使い捨てファイルへ書き、その文字列だけを最終回答として返す自己完結した内容である。ワーカーの最終回答がその文字列とバイト単位で一致することを確認する。
3. **実効ツール面**: 観測用の検証拡張から親Piの有効ツールを取得し、Pions由来のツールが3つだけであることを確認する。完了したオペレーションから、ワーカーの実効ツールが7つだけであり、`pions_delegate`を含まないことも確認する。
4. **入れ子の共有作業ディレクトリへの書き込み**: 親を新規利用先リポジトリ内の使い捨て入れ子ディレクトリから起動する。2でワーカーが相対パスに書いたファイルがその入れ子ディレクトリに存在し、内容が既知文字列と一致すること、およびオペレーションの実効`cwd`が同じ正規化済みパスであることを確認する。利用先、ファイル、ディレクトリは成功・失敗にかかわらず後始末する。
5. **ワーカーワークスペースのライフサイクル**: 2の委譲中に`herdr workspace list`と`herdr pane list`を定期的に観測し、新しく現れたワークスペースがちょうど1つで、表示名が`Pions <Operation識別子の先頭8文字>`であり、フォーカスを持たず、委譲元ワークスペースのフォーカスと唯一のペインが維持されることを確認する。委譲成功後にワーカーワークスペースが一覧から消えていること、および取得した`Operation`の表示終了処理証跡が同じワークスペース識別子の完了記録で、終了処理診断が空であることも確認する。
6. **Pi再起動後の再取得**: 2で得た`Operation`識別子を使い、別のPiプロセス(`--no-session`の新規セッション)から`pions_result`で同じ結果を取得し、本文とSHA-256ダイジェストが2と一致することを確認する。さらに`pions_operation`から完了状態、実効設定、終了処理証跡を読み、結果本文が漏れないことを確認する。
7. **開始前の設定拒否**: 検証用Pi拡張だけが登録したプロバイダーを一時利用先の`.pions.json`で指定した場合に、`pions_delegate`がエラーとなりワーカーワークスペースを作らないことを確認する。失敗した呼び出しが1回だけで自動再実行されないことも確認し、一時設定は必ず復元する。
8. **停止確認済みのキャンセル**: 検証用Pi拡張から実行中の親Pi操作をAbortし、`pions_delegate`がキャンセル結果を返すことを確認する。停止が確認された後に、その操作が所有するワーカーワークスペースだけが閉じ、`pions_operation`にキャンセル状態と終了処理完了が記録されることも確認する。
9. **Worker起動失敗時の保持**: 一時利用先にインストールしたWorker拡張だけを一時的に壊し、起動失敗が一度だけエラーとして返り、調査用ワークスペースが開いたまま残ることを確認する。終了時には拡張ファイルを復元する。

親のPiは`--mode json --no-extensions --extension <新規利用先へ導入したtarballの拡張> --approve --no-session -p @<promptファイル>`として起動する。`--no-extensions`と明示的な`--extension`は、利用者が別チェックアウトの`pions`拡張をグローバルに登録している場合の「同名ツールが競合してロードに失敗する」事故を避けるためであり、検証対象を導入済みtarballに固定する。`--approve`は今回の実行だけプロジェクトローカルファイル(`AGENTS.md`や`.pions.json`)を信頼し、共有の`~/.pi/agent/trust.json`を書き換えない。委譲されたワーカー自身は、既存の可視ワーカー実装がそのまま専用のHerdrワークスペースへ通常どおり起動する。ワーカーは`--no-extensions`で動き、Pionsはプロバイダー拡張を同梱も読み込みもしないため、`.pions.json`の`model`にはPi組み込みのプロバイダーを指定する。

## 隔離の仕組み

- 通常実行ではHerdrセッションを`pions-e2e-<pid>-<random>`という名前で毎回新規生成し、`default`セッションには触れない。監督側から`PIONS_E2E_HERDR_SESSION`と`PIONS_E2E_HERDR_COMMAND`が渡された場合はその非defaultセッションだけを使い、サーバーやセッションの起動・停止・削除を行わない。
- Herdrのライフサイクルを自分で管理する監督側は、起動済みの`default`以外のセッション名を`PIONS_E2E_HERDR_SESSION`で、そのセッションへ全呼び出しを限定するラッパー実行ファイルを`PIONS_E2E_HERDR_COMMAND`で渡せる。この場合スクリプトはHerdrサーバーの起動とセッションの停止・削除を行わず、供給されたセッション内で自分のワークスペースを作成・終了するだけになる。`PIONS_E2E_HERDR_COMMAND`は`PIONS_E2E_HERDR_SESSION`と同時に指定する。
- npm利用先を一時ディレクトリ内に作り、`.pions.json`とGitルートをそこだけに用意する。親と結果取得用のワークスペースはすべて利用先内から起動する。npmキャッシュと`XDG_STATE_HOME`も一時ディレクトリに限定し、`Operation`の永続状態や依存パッケージが利用者の状態・キャッシュと混ざらない。

## 成功時と失敗時の後始末

成功・失敗のいずれでも、作成したワークスペースを閉じ、自分で生成した隔離セッションなら`session stop`・`session delete`を実行する。成功・失敗を問わず、利用先、一時npmキャッシュ、Pions状態、ログを含む一時ディレクトリを最後に削除する。既定では失敗時にHerdrのペイン・ワークスペース一覧を標準エラーへ表示し、リポジトリ外へ診断ファイルを残さない。明示的に保存する場合だけ`PIONS_E2E_EVIDENCE_DIR`を指定する。この場合、一時利用先と診断を指定先にコピーする。

## 既知の制約

- ローカル開発機での実行を前提とし、`herdr --remote`によるリモートセッションは対象外。
- 実際のLLM呼び出しを伴うため、モデル側の応答が指示に従わない場合はまれに失敗しうる。既定では診断ファイルを残さず、明示的に`PIONS_E2E_EVIDENCE_DIR`を指定したときだけ保存する。
