# 外部着手許可と改訂の設計契約

設計元: https://github.com/yasuhito/pions/issues/33

本書は承認済みの設計であり、実装済み機能の説明ではない。#33の完了は契約、不変条件、障害時の扱い、検証条件、実装依存関係の確定だけを意味する。実装着手とプロファイル有効化はそれぞれ別途承認する。既存の読み取り委譲の既定動作は維持する。

## 責任境界

- Pionsは自身が起動したワーカーと所有ペインの終了処理、結果受理、証跡を所有する。
- コーディネーターは成果物採否、ワークスペース削除、本番テスト排他、外部資源の後始末判断を所有する。
- 書き込みワークスペースは正規ランチャーが作成・証明する。既存の共有ワークスペースには信頼済み登録アダプターによる証明も認める。
- 所有主体は具体的な識別子または不明を記録し、Pionsのワークスペース削除権限は明示的になしとする。利用権限と削除権限を混同しない。
- 資源管理は外部アダプターが所有し、Pionsは証明を検査する。署名・認証は発行元を保証するだけで、内容の正しさを保証しない。

## 起動証跡と着手ゲート

内部認証、設定照合、可視ワーカー起動の成功後、外部許可要求前に変更不能な起動証跡を永続化する。対象Operation、ワーカー実体とセッション、要求・実効・観測設定、ワークスペース識別情報と正規化された場所、起点HEAD、権限目録、レビュー対象、許可方針、絶対期限を結び付ける。証跡の読み取り権限は着手許可権限ではなく、秘密情報や他Operationの権限を公開しない。

設定方針は`required`、`optional`、`disabled`。`optional`は作成時に実効的な`required`または`disabled`へ確定し、設定と解決結果を記録する。書き込みプロファイルは必須、読み取りは信頼済み構成で選択する。正式レビューは必須とする。登録不正・接続不能を理由にゲートを無効化しない。

ゲート状態は`not_required`、`waiting`、`authorized`、`rejected`、`expired`、`invalidated`。許可済みは開始済みではなく、再照合不一致では`authorized`から`invalidated`へ進む。作業開始前の待機・停止確認中はOperationを`starting`に保つが、開始後のキャンセルで戻さない。

許可後、`begin`直前に対象一致、期限、キャンセル、有効な権限と資源証明を再検査する。不一致では証跡を差し替えず当該Operationを終了し、新規申請を要する。同じOperationで自動再起動しない。起動時照合は実行中の不変性や対象外アクセス阻止を保証しない。

## 判断・期限・公開取得

判断は認証済み主体、Operation ID、起動証跡ダイジェスト、判断ID、種別、時刻に結び付く。主体の自己申告は信用せず、作成時の許可範囲と現在も有効な認証・権限の両方を検査する。後から権限を拡大せず、失効は反映し、承認者不在でも別主体へ自動付け替えしない。

判断は原子的に永続化してから開始指示を配送する。同じ判断ID・同じ内容は冪等、異なる内容は競合。同じ内容の別判断IDでも二度目の遷移を起こさない。古い証跡、拒否・期限切れ後の許可を拒否する。許可後の停止は独立したcancel要求とし、許可判断を上書きしない。競合は監査証跡へ残す。

Operation作成時に作成時刻、許可時間枠、絶対期限を固定・永続化し、整合した記録として再取得可能にする。ワーカー起動時間も許可時間枠を消費する。証跡完成時に期限切れなら許可要求を公開しない。Pions側の判断確定時刻が期限以上なら許可しない。再接続・再送・再起動で延長しない。同一プロセスでは単調時計でも残時間を制限し、復旧時に経過時間の信頼性を確認できなければ安全側で期限切れとする。絶対時刻の保存だけで時計巻き戻り防止を保証しない。

許可待ちのコーディネーター切断だけでは拒否・失敗へ進まず、元の期限まで`starting`／`waiting`を維持する。再接続で期限を延長せず、cancelや証跡無効化など独立した正当な遷移は妨げない。

拒否は`start_rejected`、期限切れは`start_authorization_timed_out`を理由とする。判断時点で終端にせず、停止確認後に`failed`、停止を証明できなければ`unknown`とする。

公開境界は、通常のhandleによる証跡待機・読み取りと、認証済みコーディネーターの判断提出を分離する。Operation IDで証跡、状態、期限、判断、配送、停止確認、終了処理診断を再取得し、記録の版またはイベント通し番号を付けた整合したスナップショットを返す。主体が許可できる待機中Operationを列挙できるが、判断時に最新状態を再検査する。通知ではなく永続記録からの再取得を正本とする。#31の完全Result取得と公開境界を重複させない。

## 開始指示の配送と引き継ぎ

`begin`はOperation、ワーカー実体、証跡ダイジェスト、許可ID、配送世代に結び付く。同じ指示の再送では確認応答だけを再送し、プロンプト投入や実行を繰り返さない。許可判断、送信権取得、送信処理への進入、受理応答、停止確認を区別して永続化する。

送信権取得前のcancel確定は送信を阻止する。送信処理に入った後は、未配送を証明できない限り開始した可能性があるものとして停止する。確認応答未受信を未実行の証拠としない。

引き継ぎは旧配送主体の送信権失効と、ワーカー側の旧世代拒否を確認してから完了する。世代更新と`begin`受理をワーカー側で直列化し、更新応答に受理済み指示を含める。更新直前に旧世代の指示を受理した場合は回収し、取り消されたと扱わない。世代番号保存やlease期限だけを遮断証明にしない。

復旧では同じワーカー実体、認証済み接続、受理状態を照合する。未受理が確定した場合だけ期限・cancel・証跡を再検査して配送する。受理済みなら事実を回収し再実行しない。受理状態不明や受理記録喪失では安全な再送を仮定せず停止・状態確認へ進む。期限後の初回受理はワーカー側でも拒否する。引き継ぎ未完了では新規配送しない。

## ワークスペース・権限・資源証明

権限目録はツール、読み取り、書き込み、コマンド、ネットワーク、外部資源の閉じた宣言を持つ。宣言一致、観測必須、強制必須は独立した必要条件であり、単一の保証水準として比較しない。各制約の強制主体・方式の有無と観測主体・結果を分け、必要条件を満たせなければ起動を拒否する。

パスはワークスペース相対の正規化済みリテラル範囲と、全体を指定する専用値に限定する。絶対パス、glob、空要素、`.`、`..`を拒否する。シンボリックリンクや既存祖先の実体が許可範囲外へ出れば照合失敗とする。起動時の静的照合は、その後の差し替えを阻止する強制手段とは扱わない。`bash`がある読み取りプロファイルも副作用なしと仮定しない。

資源証明は資源identity、利用範囲、利用方式、実行主体、対象Operation、有効期間または世代に結び付ける。共有読み取りも含め、要求した利用方式の競合を防ぎ、引き渡しまで保証する。実行中の利用権失効時に誰が停止・遮断するかをアダプター契約へ含める。

安全性は系列ではなく影響資源に結び付ける。旧ワーカー、子プロセス、外部ジョブの停止または実効的なアクセス遮断、および競合不在と適切な引き渡しを証明できなければ、同資源を使うRetryも独立した新規Operationも開始しない。無関係な資源の利用は禁止しない。人の推測だけによる解禁は設けない。

## 固定成果物と保持

初期Review subjectは固定済みartifactだけとする。最終バイト列、バイト数、ダイジェスト方式と値、不透明な保存参照、形式と正規化規約を固定する。任意パス・任意コマンドによる検証を公開しない。許可要求前と開始直前に完全性を確認できなければ正式レビューを拒否する。

レビュー対象と必要な依存には、許可要求前の検証より先に保持参照を取得し、待機・実行・復旧中の削除を防ぐ。処理確定後に保持方針へ従って解除し、状態不明や参照利用の継続が未確認なら解除しない。

差分のbase/headは完全コミットIDの来歴であり、artifactがその差分を正しく表す証明ではない。来歴検証とバイト列完全性を別記録にする。Git差分再生成規約は初期対象外とする。

書き込み結果はテキストと要求されるWork productを一体の受理対象とする。最終バイト列と再構築に必要な起点コミット等の依存を取得・保持可能にし、部分保存では結果受理の応答を返さない。完全性は適用成功、テスト合格、成果物採用を意味しない。

保存参照はワークスペースから独立した保持方針を持つ。実効保持方針はOperation作成時に固定・永続化し、後の設定変更を既存Operationへ遡及適用しない。履歴参照は永続保持するダイジェストや採用関係、保持参照はバイト列削除を禁止するpinとして区別する。系列終了後に期限とpin解除条件を満たせば削除可能とし、取得時に方針による削除済みを破損・不明と区別する。削除可否確認とpin作成の競合を防ぎ、削除予定、実削除、完了記録の各中断点から復旧できるようにする。

## 改訂・再試行・採用

Revisionは受理済みResultを参照する線形系列で、元OperationとResultを変更しない。対象OperationとResult ID／ダイジェスト、系列起点、通し番号、理由、依頼主体、系列全体の上限を持つ。1つの結果に続くRevisionは最大1つ。予約、通し番号、上限検査、依頼IDの冪等性を原子的に永続化してから資源を作る。同一依頼IDの異なる内容は競合とする。

改訂元のResult受理は元Operationの終端や資源解放を意味しない。結果受理を根拠に資源安全確認を省略せず、残る実行と要求利用方式が競合する場合は改訂を開始しない。

Result受理前に失敗したRevisionはその地点で止まり、再実行は失敗Operationを参照する別のRetryとする。RetryのRetryでも系列全体の上限をリセットせず、Revision番号を再利用しない。すべての新Operationに新しい着手許可を要求する。`unknown`では停止と資源安全性を証明するまで予約・実行を進めない。Retry clearanceを必要とする場合は、その証拠を再取得・クラッシュ復旧可能な形で永続化した後にだけRetryを予約し、証拠の保存失敗時は予約しない。この順序を資源アダプターと予約処理の双方で保証する。一般のRevisionすべてにRetry clearanceを要求するものではなく、通常の資源安全契約は別途適用する。

Retry成功は自動採用しない。成果物採否権限を持つ主体が、正当な後続関係とResult・Work product受理を検査し、Revision番号に実際のRetry Resultを採用する不変の記録を作る。採用時に認証と対象系列への現在の成果物採否権限を再検査し、失効した主体の判断を拒否する。採用判断記録は認証済み主体、系列ID、Revision番号、Retry Operation ID、実際のResult IDとダイジェスト、判断IDを結び付ける。採用は原子的・冪等で最大1つ、別Resultへの上書きは競合。着手許可権限から採用権限を推論しない。次のRevisionは採用された実際のResultを参照する。

## 終了処理と診断

成功時は、Result受理、ワーカー停止確認、所有ペイン同一性確認、close、結果記録の順とする。失敗・拒否・期限切れ・無効化・cancel・unknownのペインは調査用に保持し、プロセス停止とは区別する。

終了処理前に処理IDと対象ペインidentityへ結び付く未完了記録を永続化する。これが保存できなければcloseせず処理不能を返す。復旧では対象状態を照合し、closeを無条件に再実行しない。完了証跡がなければ未確認とし、詳細保存失敗時も直接応答で通知する。

受理済みResultとPresentation cleanupの未確認・処理不能を独立に取得できるようにする。診断詳細の完全保存ではなく、未確認を成功に見せないことを保証する。終了処理完了だけをRetry clearanceとは扱わない。#32の二重失敗通知と接続する。

## 検証条件と段階導入

各テストは1つの振る舞いを1つのアサーションで検証する。認証主体・対象権限・失効、証跡変更、期限境界、時計不確実性、判断再送と競合、cancel競合、配送中断、世代更新直前受理、受理記録喪失、資源証明再利用、共有利用、関連実行主体残存、部分保存、pinと削除の競合、各削除中断点、採用競合、終了処理二重失敗を決定的な障害注入で検証する。

#34の完了済み思考量検査と既存回帰テストを統合検証でも再利用する。正式reviewerの外部許可は固定Review subjectの検証に依存する。Revision／Retryの有効化は停止・資源安全性の証明と終了処理復旧との接続検証に依存するが、cleanup完了だけを安全証明に代用しない。

必要な保証が揃わないプロファイルは起動を拒否する。実装Issueの完了はprofile有効化承認ではなく、統合検証の証拠と別途承認を必要とする。
